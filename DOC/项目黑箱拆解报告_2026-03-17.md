# 项目黑箱拆解报告

- 生成日期：2026-03-17
- 适用范围：当前开发态项目
- 目标：把“前端点一个按钮，后端到底怎么跑”的链路拆开，让项目不再像黑箱

---

## 1. 当前运行拓扑与端口

当前项目在开发态下的实际链路是：

```text
浏览器
  ↓ 访问
http://localhost:8081
  ↓
Vue + Vite 开发服务器
  ↓ /api 代理
http://localhost:8080
  ↓
Spring Boot 后端
  ↓
MyBatis Mapper
  ↓
MySQL:3306 / abac_control
```

### 1.1 端口表

| 层 | 地址/端口 | 来源 |
|---|---|---|
| 前端开发服务器 | `http://localhost:8081` | `frontend/abac-frontend/vite.config.js` |
| 后端服务 | `http://localhost:8080` | Spring Boot 默认端口；`application.properties` 未显式设置 `server.port` |
| 数据库 | `localhost:3306` | `backend/abac-access-control/src/main/resources/application.properties` |
| 数据库名 | `abac_control` | JDBC URL |

### 1.2 关键配置文件

- `frontend/abac-frontend/vite.config.js`
  - 前端开发端口是 `8081`
  - 所有 `/api` 请求都代理到 `http://localhost:8080`
- `backend/abac-access-control/src/main/resources/application.properties`
  - 配置了 MySQL 连接
  - 配置了 JWT secret 和过期时间
  - 没有配置 `server.port`，所以后端默认跑在 `8080`

### 1.3 一条真实请求长什么样

以“项目列表查询”为例：

```text
浏览器访问 http://localhost:8081/projects
  ↓
ProjectsView.vue 调用 queryProjects()
  ↓
http.js 发送 GET /api/project/list?pageNum=1&pageSize=8
  ↓
Vite 代理把请求转发到 http://localhost:8080/api/project/list?pageNum=1&pageSize=8
  ↓
Spring Security + JWT 认证
  ↓
ProjectController
  ↓
ProjectServiceImpl
  ↓
PEP -> PDP -> Policy
  ↓
ProjectMapper.xml 查询 projects 表
  ↓
结果回到前端页面
```

## 2. 你应该先建立的整体心智模型

这个项目可以先粗分成 6 层：

1. 前端页面层：用户点击按钮、输入表单、展示结果
2. 前端 API 层：把页面动作转成 HTTP 请求
3. 后端入口层：Controller 接收请求
4. 后端业务层：Service 做参数校验、业务编排
5. ABAC 核心层：PEP / PDP / Policy 做权限决策
6. 数据访问层：Mapper + XML 真正查库和写库

如果你把每个请求都按这 6 层去看，黑箱感会明显下降。

## 3. 全局请求总流程

绝大多数接口都遵循下面这个流程：

```text
Vue 页面
  ↓
src/api/*.js
  ↓
src/api/http.js
  ↓
Vite 代理（8081 -> 8080）
  ↓
SecurityConfig
  ↓
JwtAuthenticationFilter
  ↓
CurrentUserContext
  ↓
Controller
  ↓
Service
  ↓
PolicyEnforcementPoint
  ↓
PolicyDecisionPoint
  ↓
具体策略类
  ↓
Mapper + XML
  ↓
MySQL
```

其中最关键的 4 个“关口”是：

1. `http.js`
   - 决定是否带 `Authorization` 请求头
2. `JwtAuthenticationFilter`
   - 决定请求是不是已经登录
3. `CurrentUserContext`
   - 决定 Controller 能不能拿到当前用户 ID
4. `AbacPolicyEnforcementPoint`
   - 决定这次操作是否进入 ABAC 判断

## 4. 流程一：正常登录

这是最适合先看懂的一条链路，因为它最短。

### 4.1 请求入口

- 页面文件：`frontend/abac-frontend/src/views/LoginView.vue`
- API 文件：`frontend/abac-frontend/src/api/auth.js`
- 请求封装：`frontend/abac-frontend/src/api/http.js`

### 4.2 前端发生了什么

1. 用户打开 `http://localhost:8081/login`
2. `LoginView.vue` 里输入工号和密码
3. 点击登录后执行 `submitLogin()`
4. `submitLogin()` 调用 `login(loginForm)`
5. `login()` 在 `src/api/auth.js` 里向 `/api/employee/login` 发起 `POST`
6. `apiRequest()` 在 `src/api/http.js` 里调用 `fetch`
7. 因为这个接口不需要登录，所以此时不依赖正式 JWT

### 4.3 实际请求地址

前端看到的地址：

```text
POST http://localhost:8081/api/employee/login
```

Vite 代理后，真正到后端的是：

```text
POST http://localhost:8080/api/employee/login
```

### 4.4 后端发生了什么

- 入口 Controller：`backend/abac-access-control/src/main/java/com/xie/platform/controller/EmployeeAuthController.java`
- 业务 Service：`backend/abac-access-control/src/main/java/com/xie/platform/service/impl/EmployeeAuthServiceImpl.java`
- JWT 工具：`backend/abac-access-control/src/main/java/com/xie/platform/utils/JwtUtil.java`

处理顺序：

1. `EmployeeAuthController.login()` 接收 `EmployeeLoginDTO`
2. 调用 `employeeAuthService.login(employeeCode, password)`
3. `EmployeeAuthServiceImpl.login()` 用 `EmployeesMapper.selectByEmployeeCode()` 查员工
4. 校验员工是否存在、是否是 `ACTIVE`
5. 用 `PasswordEncoder.matches()` 比对密码
6. 如果是首次登录：
   - 调用 `JwtUtil.generateTempToken(employeeId)`
   - 返回 `tempToken`
7. 如果不是首次登录：
   - 构造 `Subject`
   - 调用 `JwtUtil.generateToken(subject)`
   - 返回正式 `token`

### 4.5 返回前端后发生了什么

- 如果是首次登录：
  - `LoginView.vue` 调用 `authStore.setTempSession(data)`
  - 前端切换到“修改密码模式”
- 如果是正常登录：
  - `authStore.setSession(data)`
  - token 写入 `localStorage`
  - 跳转到 `/projects`

### 4.6 这条链路里你最该看的文件

- `frontend/abac-frontend/src/views/LoginView.vue`
- `frontend/abac-frontend/src/api/auth.js`
- `frontend/abac-frontend/src/api/http.js`
- `backend/abac-access-control/src/main/java/com/xie/platform/controller/EmployeeAuthController.java`
- `backend/abac-access-control/src/main/java/com/xie/platform/service/impl/EmployeeAuthServiceImpl.java`
- `backend/abac-access-control/src/main/java/com/xie/platform/utils/JwtUtil.java`

## 5. 流程二：首次登录修改密码

这条线和正常登录是连着的。

### 5.1 前端流程

1. 登录返回 `mustChangePassword = true`
2. `LoginView.vue` 切换到修改密码表单
3. 执行 `submitPasswordChange()`
4. 调用 `changePassword(authStore.tempToken, passwordForm)`

### 5.2 请求地址

```text
POST http://localhost:8081/api/employee/change-password
```

代理后：

```text
POST http://localhost:8080/api/employee/change-password
```

请求头里会带：

```text
Authorization: Bearer <tempToken>
```

### 5.3 后端流程

1. `EmployeeAuthController.changePassword()` 手动读取 `Authorization`
2. 取出 `tempToken`
3. 调用 `employeeAuthService.changePassword(tempToken, oldPassword, newPassword)`
4. `EmployeeAuthServiceImpl.changePassword()` 调用 `JwtUtil.parseAndValidateTempToken()`
5. 验证临时 token 的 `scope = CHANGE_PASSWORD`
6. 查员工、校验旧密码
7. `employeesMapper.updatePassword(...)`
8. 再生成正式 JWT 并返回

### 5.4 你要特别注意

这个接口虽然也在白名单中，但它不是靠 `JwtAuthenticationFilter` 做登录判断，而是 Controller 自己从请求头里取临时 token 做校验。

所以这条流程是：

```text
前端 tempToken
  ↓
EmployeeAuthController.changePassword()
  ↓
EmployeeAuthServiceImpl.changePassword()
  ↓
JwtUtil.parseAndValidateTempToken()
```

而不是走正式 JWT 登录态。

## 6. 流程三：项目列表查询

这是你理解整个系统最重要的一条线，因为它第一次真正穿过 ABAC。

### 6.1 前端入口

- 页面：`frontend/abac-frontend/src/views/ProjectsView.vue`
- API：`frontend/abac-frontend/src/api/project.js`
- 请求封装：`frontend/abac-frontend/src/api/http.js`

### 6.2 请求地址

浏览器侧：

```text
GET http://localhost:8081/api/project/list?pageNum=1&pageSize=8
```

代理后：

```text
GET http://localhost:8080/api/project/list?pageNum=1&pageSize=8
```

### 6.3 前端过程

1. 用户进入 `/projects`
2. `router/index.js` 路由守卫判断是否已登录
3. `ProjectsView.vue` 在 `onMounted(loadProjects)` 时自动加载
4. `loadProjects()` 调用 `queryProjects(filters)`
5. `apiRequest()` 从 `authStore` 取正式 token
6. 在请求头里附带：

```text
Authorization: Bearer <token>
```

### 6.4 后端认证过程

- 文件：`backend/abac-access-control/src/main/java/com/xie/platform/security/SecurityConfig.java`
- 文件：`backend/abac-access-control/src/main/java/com/xie/platform/security/JwtAuthenticationFilter.java`
- 文件：`backend/abac-access-control/src/main/java/com/xie/platform/utils/CurrentUserContext.java`

处理顺序：

1. `SecurityConfig` 规定：除白名单外，其他请求都必须认证
2. `/api/project/list` 不在白名单，所以必须过 JWT
3. `JwtAuthenticationFilter.doFilterInternal()` 解析 `Authorization`
4. 调用 `JwtUtil.parseToken(token)`
5. 从 claims 里拿到 `employeeId`
6. 把 `employeeId` 放进 request attribute
7. 同时放进 Spring Security 的 `SecurityContextHolder`

### 6.5 Controller 到 Service

- Controller：`backend/abac-access-control/src/main/java/com/xie/platform/controller/ProjectController.java`
- Service：`backend/abac-access-control/src/main/java/com/xie/platform/service/impl/ProjectServiceImpl.java`

步骤如下：

1. `ProjectController.queryProjects()` 调用 `CurrentUserContext.getRequiredEmployeeId()`
2. 拿到当前用户 ID
3. 调用 `projectService.queryProjects(query, employeeId)`

### 6.6 Service 到数据库

`ProjectServiceImpl.queryProjects()` 做了两段事情：

第一段，先查候选数据：

1. 处理分页参数
2. 调用 `projectMapper.selectByCondition(copyQueryWithoutPagination(query))`
3. 这一步实际 SQL 在：
   - `backend/abac-access-control/src/main/resources/mapper/ProjectMapper.xml`

注意：这里先把候选项目查出来，还没有做 ABAC 拒绝。

### 6.7 Service 到 ABAC

第二段，再逐条做 ABAC：

1. 遍历 `matchedProjects`
2. 对每一条项目执行：

```text
pep.decideAccess(employeeId, buildProjectResource(project), Action.READ)
```

文件位置：

- `backend/abac-access-control/src/main/java/com/xie/platform/service/impl/ProjectServiceImpl.java`
- `backend/abac-access-control/src/main/java/com/xie/platform/access/pep/impl/AbacPolicyEnforcementPoint.java`

### 6.8 PEP 做了什么

`AbacPolicyEnforcementPoint` 是“策略执行点”，它不自己写规则，但它负责把决策所需材料准备齐。

它主要做三件事：

1. `buildSubject(employeeId)`
   - 查员工表
   - 查部门表
   - 组装 `Subject`
2. `buildEnvironment()`
   - 取当前请求时间
   - 取客户端 IP
3. 接收 Service 已经构造好的 `Resource`

最后调用：

```text
pdp.evaluate(subject, resource, action, environment)
```

### 6.9 PDP 做了什么

- 文件：`backend/abac-access-control/src/main/java/com/xie/platform/access/pdp/AbacPolicyDecisionPoint.java`

PDP 的职责是：

1. 收集所有 `Policy` 实现类
2. 按层级执行
3. 返回最终的 `DecisionResult`

当前层级顺序是：

```text
SECURITY -> PROJECT -> ROLE
```

当前真正实现的策略只有两条：

- `SecurityLevelPolicy`
- `PhaseAccessPolicy`

### 6.10 列表查询为什么看不到无权项目

因为列表接口用的是：

```text
decideAccess(...)
```

它不会直接抛异常，而是把 `isAllowed() == false` 的项目过滤掉。

所以项目列表的真实逻辑是：

```text
先查所有候选项目
  ↓
逐条执行 ABAC
  ↓
只把允许访问的项目返回给前端
```

这就是“列表级鉴权”。

## 7. 流程四：项目详情页 + 项目下资产列表

这是你理解“一个页面里同时触发两个接口”的最好例子。

### 7.1 前端入口

- 页面：`frontend/abac-frontend/src/views/ProjectDetailView.vue`
- 项目 API：`frontend/abac-frontend/src/api/project.js`
- 资产 API：`frontend/abac-frontend/src/api/asset.js`

### 7.2 页面加载时发生了什么

`ProjectDetailView.vue` 的 `loadProjectDetail()` 里做了：

```text
Promise.all([
  getProject(route.params.id),
  getAssetsByProject(route.params.id),
])
```

所以页面打开时会同时发两个请求：

1. 获取项目详情
2. 获取该项目下资产列表

### 7.3 项目详情接口流程

请求：

```text
GET http://localhost:8081/api/project/{id}
  -> 代理
GET http://localhost:8080/api/project/{id}
```

后端链路：

```text
ProjectController.getProject()
  ↓
CurrentUserContext.getRequiredEmployeeId()
  ↓
ProjectServiceImpl.getProjectById()
  ↓
pep.checkProjectAccess(employeeId, projectId, Action.READ)
  ↓
projectMapper.selectById(projectId)
```

这里用的是 `checkProjectAccess(...)`，不是 `decideAccess(...)`。

区别是：

- `decideAccess`：返回允许/拒绝结果，适合列表过滤
- `checkAccess`：如果拒绝，直接抛异常，适合详情页、删除、新增这种必须明确拒绝的场景

### 7.4 项目下资产列表流程

请求：

```text
GET http://localhost:8081/api/asset/project/{projectId}
  -> 代理
GET http://localhost:8080/api/asset/project/{projectId}
```

后端链路：

```text
ProjectAssetsController.getAssetsByProject()
  ↓
ProjectAssetsServiceImpl.getAssetsByProjectId()
  ↓
pep.checkProjectAccess(employeeId, projectId, Action.READ)
  ↓
projectAssetsMapper.selectByProjectId(projectId)
  ↓
对每条资产执行 pep.decideAssetAccess(employeeId, assetId, Action.READ)
  ↓
只返回允许访问的资产
```

### 7.5 这条链路的关键理解

项目详情页并不是“查一次项目就结束”，而是：

1. 先校验你能不能看项目
2. 再查这个项目下所有资产
3. 再逐条过滤资产

所以最终页面上“项目能看到，但某些资产不显示”是可能发生的。

## 8. 流程五：在项目详情页里创建资产

这是你理解“写操作也走 ABAC”的最好例子。

### 8.1 前端入口

- 页面：`frontend/abac-frontend/src/views/ProjectDetailView.vue`
- API：`frontend/abac-frontend/src/api/asset.js`

### 8.2 请求地址

```text
POST http://localhost:8081/api/asset/create
  -> 代理
POST http://localhost:8080/api/asset/create
```

### 8.3 前端过程

1. 用户在项目详情页填写资产表单
2. 点击“提交资产”
3. `handleCreateAsset()` 调用 `createAsset(payload)`
4. `http.js` 自动带上正式 JWT

### 8.4 后端过程

- Controller：`backend/abac-access-control/src/main/java/com/xie/platform/controller/ProjectAssetsController.java`
- Service：`backend/abac-access-control/src/main/java/com/xie/platform/service/impl/ProjectAssetsServiceImpl.java`

处理顺序：

1. `ProjectAssetsController.createAsset()`
2. `CurrentUserContext.getRequiredEmployeeId()`
3. `ProjectAssetsServiceImpl.createAsset(dto, employeeId)`
4. 校验项目 ID、资产名、类型、阶段、密级
5. 查父项目 `projectMapper.selectById(dto.getProjectId())`
6. 把前端传来的数字转成枚举
7. 关键一步：

```text
pep.checkAccess(
  creatorEmployeeId,
  Resource.builder()
    .type(ASSET)
    .projectPhase(project.getProjectPhase())
    .securityLevel(securityLevel)
    .creatorId(creatorEmployeeId)
    .build(),
  Action.WRITE
)
```

8. 如果 ABAC 允许，才会：
   - 组装 `ProjectAssets`
   - `projectAssetsMapper.insert(asset)`

### 8.5 这条线说明了什么

创建资产不是“先写库，后检查”，而是：

```text
先做 ABAC 决策
  ↓
通过后才写库
```

这说明你的 ABAC 不只管读，也在管写。

## 9. 流程六：更新项目阶段

这条线对你的毕业设计很关键，因为它体现“动态权限控制”。

### 9.1 请求地址

```text
PUT http://localhost:8081/api/project/phase
  -> 代理
PUT http://localhost:8080/api/project/phase
```

### 9.2 后端流程

```text
ProjectController.updateProjectPhase()
  ↓
ProjectServiceImpl.updateProjectPhase()
  ↓
pep.checkProjectAccess(employeeId, projectId, Action.ADVANCE_PHASE)
  ↓
projectMapper.selectById(projectId)
  ↓
projectMapper.updatePhase(projectId, newPhase)
```

### 9.3 当前实现的边界

它已经做了“你有没有资格推进阶段”的 ABAC 控制。

但它还没有做完整的流程约束，比如：

- 不能跳阶段
- 不能回退到早期阶段

所以当前逻辑更接近：

```text
有权限才允许改阶段
```

而不是：

```text
有权限 + 流程合法，才允许改阶段
```

## 10. 权限拒绝和异常是怎么回到前端的

这是黑箱里另一个经常让人迷糊的点。

### 10.1 401 未登录/令牌失效

处理文件：

- `backend/abac-access-control/src/main/java/com/xie/platform/security/JwtAuthenticationFilter.java`
- `frontend/abac-frontend/src/api/http.js`

流程：

1. `JwtAuthenticationFilter` 发现没有 Bearer Token，或者 Token 无效
2. 直接返回 `401`
3. 前端 `http.js` 收到 `401`
4. 自动执行 `authStore.clearSession()`
5. 前端登录态被清掉

### 10.2 403 权限不足

处理文件：

- `backend/abac-access-control/src/main/java/com/xie/platform/access/pep/AccessDeniedException.java`
- `backend/abac-access-control/src/main/java/com/xie/platform/exception/GlobalExceptionHandler.java`
- `backend/abac-access-control/src/main/java/com/xie/platform/common/Response.java`

流程：

1. Service 调用 `pep.checkProjectAccess(...)` 或 `pep.checkAssetAccess(...)`
2. PEP 内部如果发现 `DecisionResult.isAllowed() == false`
3. 抛出 `AccessDeniedException`
4. `GlobalExceptionHandler` 统一抓住
5. 返回：

```text
HTTP 403
Response.Forbidden(...)
```

6. 前端 `http.js` 抛出 `ApiError`
7. 页面把 `error.message` 显示出来

### 10.3 列表接口为什么通常不会报 403

因为列表用的是 `decideAccess()`，不是 `checkAccess()`。

也就是说：

- 详情页、删除、创建：拒绝时显式报错
- 列表页：拒绝时静默过滤

## 11. ABAC 核心文件职责速查

  - 登录、改密接口封装

- `frontend/abac-frontend/src/api/project.js`

- `frontend/abac-frontend/src/views/ProjectsView.vue`
  - 项目列表页

- `frontend/abac-frontend/src/views/ProjectDetailView.vue`
  - 项目详情页
  - 同时负责阶段推进和项目下资产管理

## 14. 一句话理解这个项目

这个项目在开发态下的真实结构是：

**浏览器访问 `8081` 的 Vue 页面，页面通过 `http.js` 把 `/api` 请求代理到 `8080` 的 Spring Boot 后端，后端先经过 JWT 认证，再由 Controller 和 Service 进入 PEP/PDP/Policy 的 ABAC 决策链，最后通过 Mapper + XML 访问 `3306` 上的 MySQL 数据库。**
