### 7.2 ABAC 核心模型

后端已经明确建模：

- `Subject`
- `Resource`
- `Action`
- `Environment`
- `Policy`
- `PolicyLayer`
- `PolicyResult`
- `DecisionResult`

也就是说，ABAC 论文里最核心的结构，代码层面已经基本成型。

### 7.3 已实现的真实策略

当前真正落地的策略只有两条：

1. `SecurityLevelPolicy`
2. `PhaseAccessPolicy`

它们分别负责：

- 按资源密级判断职级门槛
- 对外包人员增加限制
- 按项目阶段限制部门访问
- 对管理层设置监管型只读权限
- 对归档阶段设置只读限制

这两条策略已经足够支撑答辩中“ABAC 动态授权”的基础展示。

### 7.4 已接入业务的资源对象

当前真正被纳入 ABAC 决策的资源对象有两类：

- 项目 `Projects`
- 项目资产 `ProjectAssets`

这比纯理论版 PDP 要更进一步，因为它已经和真实业务表挂上了钩。

### 7.5 已具备的业务接口

从 Controller 和 Service 来看，目前后端已支持：

- 员工登录
- 首次登录改密
- 创建员工
- 创建项目
- 查询项目详情
- 查询项目列表
- 更新项目阶段
- 删除项目
- 创建资产
- 查询资产详情
- 查询资产列表
- 查询某项目下资产列表
- 删除资产

### 7.6 列表级鉴权

这是一处比较重要的推进。

当前项目不是只对“详情页”做鉴权，而是连下面这些列表也做了 ABAC 过滤：

- 项目列表
- 资产列表
- 某项目下资产列表

实现方式是：

1. 先按查询条件从数据库取出候选数据
2. 再在 Service 层逐条调用 PEP 做 ABAC 过滤
3. 最后返回当前用户真正有权限看到的结果

这意味着“看不到的数据不会出现在列表里”，不只是“点进去才报 403”。

## 9. ABAC 到底实现到了什么深度

这一节最重要，因为它能帮你区分“模型里有这个字段”和“规则里真的用到了这个字段”。

### 9.1 Subject 属性使用情况

| Subject 属性 | 模型中是否存在 | 当前是否进入规则 | 说明 |
|-------------|----------------|------------------|------|
| `employeeId` | 是 | 否 | 用于身份识别、创建人记录，但当前策略不按员工个人维度判断 |
| `deptId` | 是 | 否 | 已建模，但当前规则不用 |
| `deptType` | 是 | 是 | `PhaseAccessPolicy` 主要依赖它判断阶段访问 |
| `branchId` | 是 | 否 | 已建模，但当前规则不用 |
| `level` | 是 | 是 | `SecurityLevelPolicy` 用它做职级门槛判断 |
| `isContractor` | 是 | 是 | `SecurityLevelPolicy` 用它限制外包访问高密级资源 |

### 9.2 Resource 属性使用情况

| Resource 属性 | 模型中是否存在 | 当前是否进入规则 | 说明 |
|---------------|----------------|------------------|------|
| `type` | 是 | 否 | 目前更多是预留和语义区分 |
| `projectPhase` | 是 | 是 | `PhaseAccessPolicy` 主要依赖它 |
| `securityLevel` | 是 | 是 | `SecurityLevelPolicy` 主要依赖它 |
| `creatorId` | 是 | 否 | 当前没有“本人创建可特批访问”的策略 |
| `deptId` | 是 | 否 | 当前资源部门属性没有进入规则 |

### 9.3 Action 使用情况

| Action | 当前是否实际使用 | 说明 |
|--------|------------------|------|
| `READ` | 是 | 项目详情、项目列表、资产详情、资产列表 |
| `WRITE` | 是 | 创建项目、创建资产 |
| `DELETE` | 是 | 删除项目、删除资产 |
| `ADVANCE_PHASE` | 是 | 更新项目阶段 |
| `EXPORT` | 否 | 仅保留为扩展动作，当前没有导出接口 |

### 9.4 Environment 使用情况

| Environment 属性 | 模型中是否存在 | 当前是否采集 | 当前是否进入规则 |
|------------------|----------------|--------------|------------------|
| `requestTime` | 是 | 是 | 否 |
| `ipAddress` | 是 | 是 | 否 |

结论非常明确：

**当前系统已经有 ABAC 的完整建模，但真正参与决策的属性还是集中在“部门类型 + 职级 + 外包身份 + 项目阶段 + 资源密级”这 5 个核心维度上。**

也就是说，系统已经是“真 ABAC 原型”，但还不是“多维复杂 ABAC 平台”。

## 14. 当前最值得你重点注意的问题

这一节是本报告里最有实用价值的部分，因为这些问题会直接影响你后面怎么继续推进。

### 14.1 安全审计模块实际上还没做

虽然数据库备份里已经设计了 `audit_logs` 表，原始文档里也写了 `Decision -> Audit Log`，但当前代码里没有：

- 审计日志实体
- 审计日志 Mapper
- 审计日志写入逻辑
- 审计日志查询接口
- 审计日志页面

这意味着“安全审计”目前仍然停留在设计层，不在代码闭环里。

### 14.2 `/api/employee/create` 目前是公开接口

当前 `SecurityConfig` 和 `JwtAuthenticationFilter` 都把下面这个接口放到了公开白名单里：

```text
/api/employee/create
```

这意味着在当前实现下，不登录也可以创建员工。

从真实系统角度看，这是一个明显的安全风险。即使你暂时是为了开发方便，也建议尽快改成：

- 只允许管理员访问
- 或者演示阶段至少关闭该接口

### 14.3 很多属性只是“建模了”，还没有“用起来”

当前真正进入决策的属性并不多，下面这些属性虽然已经存在，但还没有进入规则：

- `Subject.employeeId`
- `Subject.deptId`
- `Subject.branchId`
- `Resource.type`
- `Resource.creatorId`
- `Resource.deptId`
- `Environment.requestTime`
- `Environment.ipAddress`

这会导致答辩时如果老师追问“为什么叫 ABAC，不是两个 if 判断”，你需要清楚解释：

当前是 **ABAC 原型系统**，而不是复杂工业版策略平台。

### 14.4 数字资产管理目前更偏“元数据管理”

当前项目资产表存的是：

- 资产名称
- 资产类型
- 阶段
- 密级
- 文件路径
- 文件大小
- 描述

但系统并没有：

- 文件上传
- 文件下载
- 在线预览
- 版本控制
- 真正的文件存储管理

所以它更像是“资产记录与权限管理系统”，而不是完整的文件管理平台。

### 14.5 阶段流转规则仍然比较粗

当前项目阶段更新虽然走了 `ADVANCE_PHASE` 鉴权，但还没有看到更严格的业务规则，例如：

- 不能从“上线交付”回退到“需求设计”
- 不能跳过中间阶段直接归档

因此它目前更像是“有权限就能改阶段”，而不是“同时满足权限规则和流程规则”。

### 14.6 列表鉴权是逐条过滤，后续会有性能压力

当前项目列表和资产列表的做法是：

- 先查全部候选数据
- 再在 Java 里逐条做 PEP 判断
- 最后分页返回

这个做法对毕设原型非常合理，但如果你后面写论文或答辩时提性能，需要主动说明：

这是一个易于展示、便于验证的原型实现，后续可以通过：

- SQL 条件下推
- 缓存
- 批量决策
- 策略预编译

继续优化。

### 14.7 配置文件里有硬编码敏感信息

`application.properties` 里当前直接写了：

- MySQL 地址
- 数据库用户名
- 数据库密码
- JWT secret

这在毕业设计环境里不是立刻不能用，但从工程规范角度看，最好后面改成环境变量或外部配置。
