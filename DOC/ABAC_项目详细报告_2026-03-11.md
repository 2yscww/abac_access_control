## 1. 项目概述

本项目的业务场景已经明确为：**企业在线数字资产管理系统**。系统面向企业内部员工、项目成员及外包人员，对项目全生命周期中产生的数字资产进行统一管理，并通过 ABAC（Attribute-Based Access Control，基于属性的访问控制）实现细粒度、动态化的权限决策。

相较于传统 RBAC，本项目更强调：

- 基于员工属性进行权限判断，如部门、职级、是否外包
- 基于资源属性进行权限判断，如项目阶段、资产密级、创建人
- 基于操作类型进行权限判断，如读取、写入、删除、推进项目阶段
- 为环境属性扩展预留能力，如请求时间、请求 IP

当前项目已经从“思路阶段”进入“系统原型与功能落地阶段”，后端核心链路基本成型，前端已搭建出完整业务壳层，具备继续联调与扩展的条件。

## 2. 本次阶段性更改说明

本次整理和开发过程中，已经完成了以下改动。这些改动目前位于工作区中，尚未提交到 Git。

### 2.1 后端改动

#### 1. 统一认证链改造

此前控制器采用“手动解析 JWT”的方式获取当前用户 `employeeId`。本次已改为统一认证方式：

- 新增 `JwtAuthenticationFilter`
- 新增 `CurrentUserContext`
- `SecurityConfig` 改为统一拦截受保护接口

这样做的效果是：

- 控制器不再关心 JWT 解析细节
- 当前登录用户可以统一从上下文获取
- 后续前端联调和权限扩展更稳定

#### 2. 统一异常返回

补充了统一异常处理机制：

- `Response` 中增加了 `Unauthorized / Forbidden / Error`
- 新增 `GlobalExceptionHandler`

这样做的效果是：

- 业务异常、鉴权异常、系统异常可以统一返回 JSON
- 前端可以更稳定地接收和展示错误信息

#### 3. 扩展 PEP 能力

原有 `PolicyEnforcementPoint` 只能针对“项目 ID / 资产 ID”做访问检查。本次扩展了以下能力：

- `decideAccess`
- `checkAccess`
- `decideProjectAccess`
- `decideAssetAccess`

这样做的效果是：

- 不仅能对已存在的项目/资产做鉴权
- 还可以对“待创建资源”的属性进行预判
- 可以为列表过滤、创建动作鉴权提供统一入口

#### 4. 项目与资产接口补全鉴权闭环

对以下场景补上了 ABAC 权限闭环：

- 创建项目
- 创建资产
- 查询项目列表
- 查询资产列表
- 查询某项目下的资产列表

此前项目详情和资产详情接口已经接入 PEP，本次重点补足了“创建”和“列表”两个容易出现越权的场景。

#### 5. 项目主键回填修复

`projects` 表是自增主键，本次修改了 `ProjectMapper.xml`，为项目创建增加了主键自动回填能力。

这样做的效果是：

- 前端创建项目后可以直接拿到 `projectId`
- 后续跳转项目详情或关联资产时更方便

#### 6. 登录接口补充 employeeId 返回

在首次登录需要改密的场景下，后端现在会额外返回 `employeeId`。

这样做的效果是：

- 前端状态可保持一致
- 后续做用户身份展示、审计展示更方便

### 2.2 前端改动

前端原先还是 Vue 默认欢迎页，本次已经搭建成完整 SPA 的基础壳层，包括：

- 登录页
- 首次登录改密流程

- 资产总览页

## 3. 项目目标与业务定位

### 3.1 业务定位

本系统面向企业数字化协作场景，核心任务是：**对项目全生命周期中的数字资产进行统一管理，并通过 ABAC 实现动态、细粒度的访问控制。**

### 3.2 核心业务对象

- 员工
- 部门
- 分公司
- 项目
- 项目资产

### 3.3 核心业务问题

企业在多部门、多项目协作中，常见以下问题：

- 不同阶段的文档与资产访问边界难以精确控制
- 同一角色在不同项目阶段权限不同
- 外包人员、低职级人员不能简单沿用统一角色权限
- 敏感资产需要按密级、阶段、操作类型联合判定

### 3.4 系统目标

- 用 ABAC 替代简单 RBAC
- 建立“员工属性 + 资源属性 + 操作属性 + 环境属性”的联合决策机制
- 实现项目与资产的动态访问控制
- 支撑后续安全审计、策略管理与扩展授权

当前由 `AbacPolicyDecisionPoint` 承担。

- 按优先级执行策略层

#### 3. PIP（策略信息点）

当前以 PEP 内部查询数据库的方式部分实现。

已支持查询：

- 员工信息
- 部门信息
- 项目信息
- 资产信息

#### 4. PAP（策略管理点）

当前尚未实现。现阶段策略仍然硬编码在后端 Java 代码中。

## 6. 当前策略设计与决策逻辑

### 6.1 策略层级

当前 PDP 采用分层策略执行机制：

1. `SECURITY`
2. `PROJECT`
3. `ROLE`

当前真正已实现的层主要是前两层：

- 安全策略层
- 项目策略层

`ROLE` 层目前仍是预留位。

### 6.2 安全策略层

当前核心策略为 `SecurityLevelPolicy`。

规则核心：

- 资源密级越高，所需职级越高
- 外包员工禁止访问 `CONFIDENTIAL` 及以上密级资源

该策略体现了：

- 密级控制
- 职级门槛控制
- 外包人员额外限制

### 6.3 项目策略层

当前核心策略为 `PhaseAccessPolicy`。

规则核心：

- 不同项目阶段允许访问的部门不同
- 管理层在特定阶段有只读监管能力
- 归档阶段仅允许管理层只读访问

该策略体现了：

- 动态阶段控制
- 部门边界控制
- 监管型访问控制

### 6.4 裁决逻辑

当前 PDP 逻辑如下：

- 高优先级策略先执行
- 任意层命中 `DENY`，立即终止
- 若命中 `FORCE_ALLOW`，跳过后续层
- 所有策略通过则默认允许

## 9. 当前系统核心流程

以下为当前系统已经能够支撑的主要业务流程。

### 9.1 登录与首次改密流程

流程如下：

1. 用户在前端输入工号和密码
2. 前端请求 `/api/employee/login`
3. 后端校验员工状态、密码、是否首次登录
4. 若首次登录，返回临时 token
5. 前端进入改密流程
6. 用户修改密码后，请求 `/api/employee/change-password`
7. 后端返回正式 JWT
8. 前端保存 token 并进入系统主页

### 9.2 统一接口认证流程

流程如下：

1. 前端携带 `Authorization: Bearer <token>` 请求接口
2. Spring Security 先进入过滤链
3. `JwtAuthenticationFilter` 解析 token
4. 将当前 `employeeId` 放入请求上下文
5. Controller 通过 `CurrentUserContext` 获取当前用户
6. 进入业务处理

### 9.3 ABAC 决策流程

流程如下：

1. Service 调用 PEP
2. PEP 查询员工、部门、项目、资产数据
3. PEP 组装 Subject / Resource / Action / Environment
4. PEP 调用 PDP
5. PDP 按层级执行安全策略和项目策略
6. 若拒绝，则返回拒绝结果
7. 若允许，则业务继续执行

### 9.4 项目访问流程

当用户查看项目详情或项目列表时：

1. 获取当前用户属性
2. 获取目标项目属性
3. 对项目执行 `READ` 权限判断
4. 若允许，返回项目信息
5. 若拒绝，返回 403

### 9.5 项目创建流程

1. 用户在前端填写项目名称、阶段、密级
2. 后端构造“待创建项目”的 Resource 属性
3. PEP 对创建动作执行 `WRITE` 决策
4. 若允许，则写入数据库
5. 返回新建项目 ID

### 9.6 项目阶段推进流程

1. 用户在项目详情页选择新阶段
2. 请求后端更新项目阶段
3. PEP 对该项目执行 `ADVANCE_PHASE`
4. 若允许，则更新数据库中的项目阶段
5. 若拒绝，则返回拒绝信息

### 9.7 资产创建流程

1. 用户进入某项目详情页
2. 填写资产名称、类型、阶段、密级等信息
3. 后端先读取所属项目
4. 构造“资产资源属性”
5. 对 `WRITE` 执行 ABAC 决策
6. 若允许，则创建资产

### 9.8 列表查询流程

当前项目列表与资产列表的实现流程为：

1. 先按查询条件从数据库取出候选数据
2. 再对结果集逐条执行 ABAC 过滤
3. 仅把当前用户允许访问的数据返回前端

说明：

- 这种方案适合当前毕设阶段快速落地与展示
- 但在大数据量场景下还需要进一步优化
