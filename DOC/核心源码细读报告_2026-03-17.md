## 1. 先说结论

你现在的“看不懂”，主要不是因为业务本身复杂，而是因为项目里同时混了 3 种东西：

1. Spring 框架写法
2. ABAC 领域模型
3. 业务本身的项目/资产逻辑

如果直接看源码，大脑会在这 3 层之间来回跳，所以很容易产生黑箱感。

你现在最需要的，不是继续多看文件，而是先把下面这几个概念彻底吃透：

- Spring 怎么把类自动连起来
- JWT 怎么把“当前用户”一路传到 Controller
- PEP 和 PDP 各自负责什么
- 列表过滤和详情拒绝为什么写法不一样

## 2. 先把框架写法翻译成人话

这部分建议你先看完，再去读业务代码。

### 2.1 `@Component` / `@Service` / `@Configuration` 是什么

它们本质上都在做一件事：

**告诉 Spring：“这个类交给你来创建和管理。”**

区别只是语义不同：

- `@Component`
  - 普通组件
  - 例如 `JwtAuthenticationFilter`、`AbacPolicyEnforcementPoint`
- `@Service`
  - 业务服务类
  - 例如 `ProjectServiceImpl`
- `@Configuration`
  - 配置类
  - 例如 `SecurityConfig`

你可以先把它们理解成：

```text
@Component / @Service / @Configuration
= “这个类不要手动 new，Spring 会帮我创建”
```

### 2.2 `@Autowired` 是什么

它的意思是：

**这个字段我不自己 new，让 Spring 把合适的对象塞进来。**

例如：

```java
@Autowired
private ProjectMapper projectMapper;
```

你可以把它理解成：

```text
我需要一个 ProjectMapper，请 Spring 帮我准备好
```

### 2.3 为什么很多地方都不是 `new Xxx()`？

因为这是 Spring 项目。

像下面这些对象：

- `ProjectServiceImpl`
- `JwtAuthenticationFilter`
- `AbacPolicyEnforcementPoint`
- `PasswordEncoder`

都不是你手动创建的，而是 Spring 在启动时统一创建，再注入到需要的类里。

所以你读代码时，不要问：

> “这个对象在哪里 new 的？”

要改成问：

> “这个对象是不是 Spring Bean？如果是，它是被谁注入进来的？”

### 2.4 接口 + 实现类为什么分开

比如：

- `PolicyEnforcementPoint` 是接口
- `AbacPolicyEnforcementPoint` 是实现类

这表示：

```text
接口 = 先定义能力
实现类 = 再写具体做法
```

好处是业务层只依赖“能力”，不依赖“具体类”。

所以在 `ProjectServiceImpl` 里你看到的是：

```java
private PolicyEnforcementPoint pep;
```

而不是直接写实现类。

这意味着业务层只关心：

```text
我需要一个“能做权限判断”的东西
```

至于它具体叫 `AbacPolicyEnforcementPoint`，业务层不想知道。

### 2.5 `Builder` 是什么

你经常会看到：

```java
Resource.builder()
    .type(ResourceType.PROJECT)
    .projectPhase(projectPhase)
    .securityLevel(securityLevel)
    .creatorId(creatorEmployeeId)
    .build();
```

这只是另一种构造对象的写法，目的是让代码更清楚。

你可以把它翻译成：

```text
我要组装一个 Resource 对象，
它的 type 是 PROJECT，
projectPhase 是 xxx，
securityLevel 是 xxx，
creatorId 是 xxx
```

### 2.6 `stream().filter().toList()` 是什么

例如项目列表里：

```java
matchedProjects.stream()
    .filter(project -> pep.decideAccess(...).isAllowed())
    .toList();
```

本质上只是：

```text
把原列表挨个检查一遍
只保留满足条件的项
最后生成新列表
```

也就是：

```text
for 循环 + if 判断 + 把满足条件的元素放进新列表
```

## 4. 认证链路细读

这一组文件决定“用户是谁”。

### 4.1 `SecurityConfig.java`

文件：

- `backend/abac-access-control/src/main/java/com/xie/platform/security/SecurityConfig.java`

它解决的问题是：

**哪些接口可以直接访问，哪些接口必须登录。**

#### 关键代码解释

- 第 17 到 38 行：定义 `SecurityFilterChain`
  - 这是 Spring Security 的主配置入口

- 第 23 行：`.csrf(csrf -> csrf.disable())`
  - 关闭 CSRF
  - 对纯前后端分离项目很常见

- 第 24、25 行：关闭表单登录和 httpBasic
  - 说明项目不用 Spring 默认登录页
  - 也不用浏览器弹窗认证

- 第 26 行：`STATELESS`
  - 表示后端不保存 session
  - 每次请求都要自己带 token
  - 这是 JWT 项目最常见的配置

- 第 27 到 34 行：授权规则
  - `/api/employee/login` 放行
  - `/api/employee/change-password` 放行
  - `/api/employee/create` 放行
  - 其余请求都必须认证

- 第 35 行：把 `jwtAuthenticationFilter` 插到用户名密码过滤器之前
  - 意思是：
  - 在进入 Controller 之前，先跑 JWT 校验

#### 读这个文件时最容易误解的点

你可能会以为它在做“权限控制”。

其实不是。

它只做两件事：

1. 登录态校验
2. 白名单放行

真正的 ABAC 权限控制不在这里，而是在 Service -> PEP -> PDP 里。

---

### 4.2 `JwtAuthenticationFilter.java`

文件：

- `backend/abac-access-control/src/main/java/com/xie/platform/security/JwtAuthenticationFilter.java`

它解决的问题是：

**把请求头里的 JWT 解析出来，变成“当前登录用户”。**

#### 关键代码解释

- 第 29 到 33 行：`PUBLIC_PATHS`
  - 白名单路径
  - 和 `SecurityConfig` 基本一致

- 第 45 到 47 行：`shouldNotFilter`
  - 如果请求在白名单里，就不跑这个过滤器
  - 例如登录接口

- 第 55 行：读取请求头 `Authorization`

- 第 56 到 58 行：
  - 如果没有 `Bearer ` 开头的 token
  - 直接返回 401

- 第 62 行：
  - 去掉前缀 `"Bearer "`，只留下 token 字符串

- 第 63 行：
  - 调用 `jwtUtil.parseToken(token)`
  - 真正解析 JWT

- 第 64 行：
  - 从 token 里拿出 `subject`
  - 这里项目把 `subject` 存成了员工 ID

- 第 66 行：
  - 把 `employeeId` 塞进 request attribute
  - 这是给 `CurrentUserContext` 用的

- 第 68 到 71 行：
  - 再把 `employeeId` 塞进 `SecurityContextHolder`
  - 这是给 Spring Security 用的

- 第 73 行：
  - 放行到后续链路
  - 包括 Controller、Service 等

- 第 74 到 76 行：
  - 如果 token 解析失败，就返回 401

#### 最容易看不懂的点 1：为什么同时放到 request 和 SecurityContext？

因为项目想兼容两种取法：

1. 从 request attribute 取
2. 从 Spring Security 上下文取

而 `CurrentUserContext` 的写法是：

```text
先取 request attribute
如果没有，再取 SecurityContext
```

所以这里是双保险。

#### 最容易看不懂的点 2：第 77 到 79 行 `clearContext()` 会不会把用户清掉？

不会影响当前 Controller 的执行。

原因是：

1. `filterChain.doFilter(...)` 已经把请求继续传下去了
2. Controller 执行期间，request attribute 还在
3. `CurrentUserContext` 优先读的是 request attribute

所以这里虽然看起来可疑，但当前代码并不会把当前请求搞坏。

不过它确实值得后面再审视一下。

---

### 4.3 `CurrentUserContext.java`

文件：

- `backend/abac-access-control/src/main/java/com/xie/platform/utils/CurrentUserContext.java`

它解决的问题是：

**让 Controller 能方便拿到当前登录用户 ID。**

#### 关键代码解释

- 第 11 行：定义 request attribute 的 key
  - 这个 key 和过滤器里写入的 key 对应

- 第 16 到 44 行：`getEmployeeId()`
  - 先从当前请求里取 employeeId
  - 如果取不到，再尝试从 Spring Security 上下文里取

- 第 17 到 26 行：
  - 这是“从 request 取”的逻辑
  - 也就是读取过滤器刚才塞进去的值

- 第 28 到 41 行：
  - 这是“从 SecurityContext 取”的逻辑
  - 属于兜底方案

- 第 46 到 52 行：`getRequiredEmployeeId()`
  - 如果没取到当前用户，直接抛 `BizException`

#### 这个文件的本质

你可以把它理解成：

```text
Controller 专用的“当前登录用户工具类”
```

所以 Controller 里看到：

```java
Long employeeId = CurrentUserContext.getRequiredEmployeeId();
```

其实就是：

```text
把当前请求对应的登录用户 ID 拿出来
```

## 5. 登录服务细读

这一组文件决定“登录成功后怎么生成 token”。

### 5.1 `EmployeeAuthServiceImpl.java`

文件：

- `backend/abac-access-control/src/main/java/com/xie/platform/service/impl/EmployeeAuthServiceImpl.java`

它解决的问题是：

1. 登录
2. 首次登录改密
3. 创建员工

### 5.2 `login()` 方法怎么读

方法位置：

- 第 43 到 100 行

你可以把它分成 5 段。

#### 第一段：查员工

- 第 47 行：

```java
Employees employee = employeesMapper.selectByEmployeeCode(employeeCode);
```

意思就是：

```text
根据工号查数据库里的员工
```

#### 第二段：做基本校验

- 第 51 到 67 行

依次判断：

1. 员工是否存在
2. 员工是否在职
3. 密码是否正确

这里没有抛异常，而是往 `LoginResult` 里写失败信息并返回。

也就是说：

```text
登录失败被当成“正常业务结果”
不是系统异常
```

#### 第三段：设置登录成功的基础信息

- 第 69 到 73 行

包括：

- 登录是否成功
- employeeId
- 是否必须改密码
- 登录成功消息

#### 第四段：首次登录只发临时 token

- 第 77 到 81 行

如果 `mustChangePassword = true`：

- 不发正式 JWT
- 只发 `tempToken`

这是为了强制用户先改密码再进系统。

#### 第五段：非首次登录才发正式 JWT

- 第 83 到 97 行

这里做了两件事：

1. 构造 `Subject`
2. 调用 `jwtUtil.generateToken(subject)`

注意：

这里虽然构造了 `Subject`，但 JWT 里其实没有把 Subject 所有字段都塞进去。
当前 token 里真正写进去的主要是：

- employeeId
- deptId
- level

其它 ABAC 属性还是在 PEP 阶段重新查库拿的。

#### 为什么登录时要构造 `Subject`，后面 PEP 还要再构造一遍？

因为两者用途不同：

- 登录时构造 `Subject`
  - 主要是为了生成 token
- PEP 时构造 `Subject`
  - 主要是为了真实 ABAC 决策

所以它们不是重复逻辑，而是不同阶段复用了同一组领域概念。

---

### 5.3 `changePassword()` 方法怎么读

方法位置：

- 第 103 到 135 行

这段逻辑也可以拆成 5 段。

1. 解析临时 token
2. 根据 token 取 employeeId
3. 查员工
4. 校验旧密码
5. 更新密码后生成正式 token

#### 为什么这里不是直接生成新密码就完？

因为“改密成功”在当前系统里等价于：

```text
完成首次登录流程
正式获得进入系统的资格
```

所以改密成功后，系统顺手发正式 JWT。

---

### 5.4 `createEmployee()` 方法怎么读

方法位置：

- 第 137 到 197 行

它本质上是：

1. 校验 DTO
2. 校验部门和分公司是否存在
3. 把前端传的 level 数字转成枚举
4. 生成默认密码
5. 创建员工记录
6. 插入数据库后回填员工工号

#### 最容易看不懂的点

- 第 181 行：

```java
employee.setEmployeeCode("PENDING");
```

这不是正式工号，只是临时占位。

因为数据库主键 `employeeId` 还没生成出来，真正工号要等 insert 完之后才能根据 `employeeId + 1000` 回填。

## 6. ABAC 的数据对象到底是什么

读 PEP 和 PDP 之前，你必须先搞清楚 `Subject`、`Resource`、`DecisionResult` 这三个对象。

### 6.1 `Subject.java`

文件：

- `backend/abac-access-control/src/main/java/com/xie/platform/access/subject/Subject.java`

它表示：

**谁在访问。**

字段含义：

- `employeeId`
  - 员工 ID
- `deptId`
  - 部门 ID
- `deptType`
  - 部门类型，例如产品、研发、测试、管理层
- `branchId`
  - 分公司 ID
- `level`
  - 员工职级
- `isContractor`
  - 是否外包

### 6.2 `Resource.java`

文件：

- `backend/abac-access-control/src/main/java/com/xie/platform/access/resource/Resource.java`

它表示：

**被访问的东西是什么。**

字段含义：

- `type`
  - 项目还是资产
- `projectPhase`
  - 当前项目阶段
- `securityLevel`
  - 密级
- `creatorId`
  - 创建人
- `deptId`
  - 资源所属部门

注意：

PDP 不直接依赖 `Projects` 或 `ProjectAssets` 实体，而是依赖 `Resource`。

这是为了让 ABAC 决策层和具体业务实体解耦。

### 6.3 `DecisionResult.java`

文件：

- `backend/abac-access-control/src/main/java/com/xie/platform/access/pdp/DecisionResult.java`

它表示：

**这次权限判断的最终结果。**

字段只有 3 个：

- `allowed`
  - 是否允许
- `triggerPolicy`
  - 是哪条策略触发了最终结果
- `reason`
  - 给人看的原因

这个对象很关键，因为它是：

```text
ABAC 最终输出
```

后面如果你做审计日志，这个对象几乎一定会被用到。

## 7. PEP 细读

PEP 是“策略执行点”，文件是：

- `backend/abac-access-control/src/main/java/com/xie/platform/access/pep/impl/AbacPolicyEnforcementPoint.java`

它解决的问题是：

**在真正进入 PDP 之前，把决策所需的材料准备齐。**

### 7.1 先理解一句话

PEP 不负责决定“允许还是拒绝”。

PEP 负责的是：

```text
把 Subject / Resource / Action / Environment 准备好
然后交给 PDP 判
```

### 7.2 `decideAccess()` 怎么读

- 第 47 到 52 行

它只做 3 步：

1. `buildSubject(employeeId)`
2. `buildEnvironment()`
3. `pdp.evaluate(subject, resource, action, environment)`

也就是说：

```text
PEP = 组装材料 + 调用 PDP
```

### 7.3 `checkAccess()` 和 `decideAccess()` 有什么区别

- `decideAccess()`
  - 返回 `DecisionResult`
  - 常用于列表过滤

- `checkAccess()`
  - 内部先调用 `decideAccess()`
  - 如果拒绝，直接抛 `AccessDeniedException`
  - 常用于详情、新增、删除等必须显式拒绝的场景

这个区别非常关键。

你可以记成：

```text
decide = 只算结果
check = 结果不通过就直接报错
```

### 7.4 `decideProjectAccess()` / `decideAssetAccess()` 为什么存在

因为有两种调用场景：

1. 业务层已经自己组好了 `Resource`
2. 业务层只有 `projectId` 或 `assetId`

如果业务层只有 ID，PEP 就负责再去查数据库，把它转换成 `Resource`。

### 7.5 `buildSubject()` 怎么读

- 第 92 到 111 行

逻辑是：

1. 根据 `employeeId` 查员工
2. 根据员工的 `deptId` 查部门
3. 把员工信息和部门类型拼成 `Subject`

注意：

这里说明一个事实：

**ABAC 决策时真正使用的主体属性，不是完全从 JWT 里取的，而是实时查库得到的。**

### 7.6 `buildResourceForProject()` 怎么读

- 第 113 到 126 行

逻辑是：

1. 根据 `projectId` 查项目
2. 从项目实体中提取 PDP 真正需要的字段
3. 组装成 `Resource`

注意这里不是把整个 `Projects` 对象扔给 PDP，而是只抽取：

- type
- projectPhase
- securityLevel
- creatorId

这说明设计上是在做“领域抽象”，不是把业务实体直接塞给权限引擎。

### 7.7 `buildResourceForAsset()` 怎么读

- 第 128 到 146 行

这里比项目多一步：

1. 先查资产
2. 再查资产所属项目
3. 取资产自己的密级
4. 取父项目当前阶段
5. 组装 `Resource`

这说明一个重要事实：

**资产权限判断会同时受资产密级和项目阶段影响。**

### 7.8 `buildEnvironment()` 怎么读

- 第 148 到 166 行

目前它只采集两个环境属性：

- `requestTime`
- `ipAddress`

虽然代码采集了环境属性，但当前策略并没有真正使用它们。

所以这部分目前更像是：

```text
为后续环境策略预留
```

## 8. PDP 细读

文件：

- `backend/abac-access-control/src/main/java/com/xie/platform/access/pdp/AbacPolicyDecisionPoint.java`

它解决的问题是：

**真正决定允许还是拒绝。**

### 8.1 先理解一句话

PDP 不查数据库、不关心 HTTP、不关心前端。

它只做这件事：

```text
拿到 Subject / Resource / Action / Environment
按规则算出结果
```

### 8.2 `allPolicies` 是怎么来的

- 第 35 到 36 行

```java
@Autowired
List<Policy> allPolicies;
```

Spring 会自动把所有实现了 `Policy` 接口、并且被注册为 Bean 的类收集起来。

也就是说：

- `SecurityLevelPolicy`
- `PhaseAccessPolicy`

会自动进入这个列表。

所以你以后新增策略，只要：

1. 实现 `Policy`
2. 加上 `@Component`

PDP 就能自动拿到它。

### 8.3 `init()` 为什么存在

- 第 51 到 55 行

它把 `allPolicies` 按 `PolicyLayer` 分组，存进 `policyMap`。

意思是把策略整理成：

```text
SECURITY 层有哪些策略
PROJECT 层有哪些策略
ROLE 层有哪些策略
```

这样后面执行时更方便。

### 8.4 `LAYER_ORDER` 为什么重要

- 第 45 到 49 行

这是当前项目的层级优先级：

```text
SECURITY -> PROJECT -> ROLE
```

这意味着：

1. 先检查密级/安全层
2. 再检查项目阶段/部门层
3. 最后才是角色属性层

虽然现在 `ROLE` 层还没有真正实现的策略，但框架已经预留好了。

### 8.5 `evaluate()` 怎么读

这是整个 PDP 的核心，位置：

- 第 57 到 85 行

逻辑是双层循环：

1. 先按层循环
2. 每层里再逐条策略循环

#### 规则执行逻辑

对于每条策略的结果：

- `ALLOW`
  - 说明这条策略没有拦你
  - 继续看后面的策略

- `DENY`
  - 立刻拒绝
  - 直接返回 `DecisionResult.deny(...)`

- `FORCE_ALLOW`
  - 立刻放行
  - 跳过所有后续层

#### 为什么默认是 `allow()`

- 第 83 到 84 行

因为当前设计是：

```text
没有任何策略明确拒绝
=> 默认允许
```

这是一种常见设计，但它要求你的策略写得足够严谨。

### 8.6 `buildDenyReason()` 有什么用

- 第 87 到 94 行

它把“拒绝原因”变成人能看懂的话。

例如：

- 安全层拒绝 -> `安全策略拒绝：SecurityLevelPolicy`
- 项目层拒绝 -> `项目策略拒绝：PhaseAccessPolicy`

这个方法的作用主要是：

```text
增强可解释性
```

## 9. 两条策略怎么读

### 9.1 `SecurityLevelPolicy.java`

文件：

- `backend/abac-access-control/src/main/java/com/xie/platform/access/policy/impl/SecurityLevelPolicy.java`

它解决的问题是：

**这个人的职级和身份，够不够看这个密级的资源。**

#### `evaluate()` 的真实逻辑

- 第 48 到 50 行：
  - 如果资源没有密级，或主体没有职级
  - 这条策略就不介入
  - 直接 `ALLOW`

这不是“允许访问”，更准确地说是：

```text
这条策略不发表意见
```

#### 第一个判断：外包限制

- 第 53 到 59 行

规则是：

```text
如果是外包
且资源密级 >= CONFIDENTIAL
=> 直接拒绝
```

#### 第二个判断：职级门槛

- 第 61 到 65 行

规则是：

```text
员工职级 rank >= 该密级要求的最低 rank
=> 允许
否则拒绝
```

#### `getRequiredRank()` 的作用

- 第 76 到 84 行

它就是一个映射表：

- PUBLIC -> 1
- INTERNAL -> 3
- CONFIDENTIAL -> 5
- TOP_SECRET -> 9

本质上就是把业务规则写成代码。

### 9.2 `PhaseAccessPolicy.java`

文件：

- `backend/abac-access-control/src/main/java/com/xie/platform/access/policy/impl/PhaseAccessPolicy.java`

它解决的问题是：

**当前项目阶段下，这个部门能不能做这件事。**

#### `evaluate()` 的真实逻辑

- 第 49 到 51 行：
  - 如果资源没有阶段，或者主体没有部门类型
  - 本策略不介入

#### 第一段：归档阶段

- 第 54 到 60 行

规则是：

```text
如果项目已归档：
  只有 MANAGEMENT 能访问
  且只能 READ
```

#### 第二段：普通阶段按矩阵放行

- 第 62 到 66 行

根据当前阶段查允许访问的部门集合：

- INIT -> PRODUCT, MANAGEMENT
- REQUIREMENT -> PRODUCT, RD
- DEVELOPMENT -> RD, PRODUCT
- TEST -> QA, RD
- RELEASE -> OPS, RD

如果当前用户部门在集合里，就允许。

#### 第三段：管理层只读兜底

- 第 68 到 70 行

如果不在完整访问集合中，但用户是管理层：

- 允许 READ
- 禁止写删改

#### 最终兜底

- 第 73 行：

```java
return PolicyResult.DENY;
```

意思是：

```text
不满足前面任何放行条件
=> 拒绝
```

## 10. 业务 Service 怎么读

### 10.1 `ProjectServiceImpl.java`

它解决的问题是：

**项目相关业务。**

最关键的方法有 5 个。

#### `createProject()`

- 第 35 到 85 行

逻辑顺序：

1. 校验项目名和密级
2. 检查项目名是否重复
3. 把前端传来的数字转成枚举
4. 用 `pep.checkAccess(..., Action.WRITE)` 做 ABAC
5. ABAC 通过后才插库

要点：

```text
写操作是“先鉴权，再入库”
```

#### `getProjectById()`

- 第 88 到 100 行

顺序是：

1. 判空
2. `pep.checkProjectAccess(..., Action.READ)`
3. 查库

这说明详情页是强校验：

```text
无权就直接 403
```

#### `queryProjects()`

- 第 103 到 113 行

这是最关键的列表接口。

逻辑是：

1. 先查数据库候选项目
2. 再逐条执行 ABAC
3. 过滤出允许访问的项目
4. 最后手动分页

你可能会奇怪：

> 为什么不先分页再鉴权？

因为当前实现希望：

```text
用户最终看到的分页结果，是权限过滤后的结果
```

代价就是性能一般，但原型阶段合理。

#### `updateProjectPhase()`

- 第 117 到 144 行

流程：

1. 校验参数
2. `pep.checkProjectAccess(..., ADVANCE_PHASE)`
3. 查项目
4. 校验新阶段是否合法
5. 已归档项目不允许改阶段
6. 更新数据库

#### `deleteProject()`

- 第 148 到 160 行

顺序很标准：

1. 判空
2. 先鉴权
3. 再查项目是否存在
4. 删除

### 10.2 `ProjectAssetsServiceImpl.java`

它和项目 Service 非常像，只是资源对象换成了资产。

#### `createAsset()`

- 第 40 到 107 行

最关键的一点是：

创建资产时构造 `Resource` 用的是：

- 资产自己的 `securityLevel`
- 父项目当前的 `projectPhase`

所以当前 ABAC 是：

```text
资产权限 = 资产密级 + 所属项目阶段
```

#### `getAssetsByProjectId()`

- 第 125 到 135 行

这里有两层判断：

1. 先判断你能不能看这个项目
2. 再把这个项目下的资产逐条过滤

所以你会看到一种现象：

```text
你能进入项目详情页
但并不一定能看到项目下所有资产
```

#### `queryAssets()`

- 第 138 到 148 行

和项目列表一样：

```text
先查候选资产
再逐条做 ABAC 过滤
最后手动分页
```

## 11. 前端最容易卡住的两个文件

### 11.1 `http.js`

文件：

- `frontend/abac-frontend/src/api/http.js`

它不是某个具体业务接口，而是：

**所有请求的统一壳层。**

#### 关键点

- 第 13 到 25 行：`buildQuery`
  - 把 JS 对象拼成 URL 查询参数

- 第 27 到 34 行：解构参数
  - `method`、`body`、`query`、`token`

- 第 40 到 43 行：
  - 如果调用方手动传了 `token`，优先用它
  - 否则默认用 `authStore.token`

这就是为什么：

- 正常登录后，大多数接口自动带正式 JWT
- 修改密码接口可以手动传 `tempToken`

- 第 45 到 49 行：
  - 真正发 `fetch`

- 第 58 到 68 行：
  - 同时检查 HTTP 状态码和业务 `code`
  - 只要任一层失败，就抛 `ApiError`

- 第 60 到 62 行：
  - 如果是 401，自动清空前端会话

#### 这个文件的本质

你可以把它理解成：

```text
前端版的“统一请求过滤器”
```

### 11.2 `auth.js` 和 `router/index.js`

#### `stores/auth.js`

它解决的问题是：

**前端如何记住我已经登录。**

关键逻辑：

- `token`
  - 正式登录态
- `tempToken`
  - 首次改密专用
- `isAuthenticated`
  - 只看正式 token 是否存在

这说明：

```text
有 tempToken 不代表真正登录进系统
```

#### `router/index.js`

它解决的问题是：

**哪些页面必须登录才能进。**

关键逻辑：

- 如果目标路由 `requiresAuth = true`
- 且当前没有正式 token
- 就跳到 `/login`

所以前端页面访问控制，本质上只认正式 token。

## 12. 你现在最容易卡住的 8 个细节

### 12.1 “为什么 Controller 里几乎没有业务逻辑？”

因为项目采用的是：

```text
Controller 只接请求
Service 才放业务逻辑
```

所以 Controller 很薄，这是正常设计。

### 12.2 “为什么业务代码里到处在用接口，不直接调实现类？”

因为 Spring 推荐依赖抽象，不依赖具体实现。

你可以先忽略“实现类名”，只看接口名表达的能力。

### 12.3 “为什么登录时生成 Subject，后面 PEP 又构建 Subject？”

因为登录和鉴权是两个阶段：

- 登录阶段：主要为了发 token
- 鉴权阶段：主要为了做实时 ABAC

### 12.4 “为什么列表接口不直接 403，而是返回更少的数据？”

因为列表用的是：

```text
decideAccess -> 过滤
```

详情/删除/写操作用的是：

```text
checkAccess -> 报错
```

### 12.5 “为什么 PEP 里还要查库，不是已经拿到 employeeId 了吗？”

因为 employeeId 只是“谁”。

ABAC 还需要知道：

- 他属于什么部门
- 什么职级
- 是否外包

这些都得从数据库里补全。

### 12.6 “为什么 Resource 里资产也要带 projectPhase？”

因为资产权限不只看资产自己，还看它所在项目的阶段。

### 12.7 “为什么 PDP 没有 if-else 写死在 Service 里？”

因为项目在做职责分离：

- Service 负责业务编排
- PEP 负责准备决策材料
- PDP 负责做决策
- Policy 负责表达单条规则

这就是 ABAC 架构的核心价值之一。

### 12.8 “为什么很多地方信息不足时直接 ALLOW？”

这里的 `ALLOW` 更准确地说是：

```text
当前这条策略不介入
```

最终结果仍然要看其它策略是否拒绝。

## 14. 最后一句话

你现在真正需要掌握的不是“所有代码细节”，而是：

**每个类在整个链路里到底扮演什么角色。**

一旦你能把下面这句话自己复述出来，你对项目的理解就会明显提升：

> 前端把 token 带到后端，过滤器解析出当前用户，Controller 拿到 employeeId，Service 组织业务，PEP 组装 Subject/Resource/Environment，PDP 按策略层级做决策，最后再决定是否允许查库或写库。
